FRAUD_WATCH: Autonomous MLOps Agent

Westpac demo runbook. Snowflake account SFSEAPAC-AZAU_ANUDEEP, database FRAUD_AUTOML_DEMO, repo sfc-gh-aayinaparthi/fraud-mlops-agent-demo

1. The story in one paragraph

A fraud model normally flags about 2% of card transactions. An engineer merges a sensible-looking performance refactor: read 30-day customer spend from the new customer-profile platform instead of scanning 30 days of transactions. The new table was backfilled from a 1 November snapshot, so cards issued since then have no profile. For those cards the feature goes NULL, a defensive COALESCE(..., 1) turns the "amount vs usual spend" ratio into roughly 50x, and the model starts declining legitimate new-card customers. About 10% of traffic is affected and the flag rate jumps from about 0.8% (daytime) to about 11%.

FRAUD_WATCH, a Cortex Code cloud automation, finds the spike, works out where it is concentrated, links it to the deploy through lineage, proves the cause by re-scoring the window with the previous pipeline version, opens a revert PR and emails a full incident report. A human merges the PR, and the rate returns to normal.

4. Demo flow (about 12 minutes)

4.1 Baseline (2 min)

Show the Model Registry (two versions, metrics), the model monitor, and the predictions table with its version stamps.

"Every prediction is stamped with the exact code and model that produced it. That's the precondition for an agent being able to reason about cause."

4.2 The bad change (1 min)

uv run python scripts/scenario.py inject

This opens and merges a real PR ("perf: use customer profile v2"), and CI deploys pipeline V2. Show the PR diff: it looks reasonable.

"Nothing failed. No error, no alert. The pipeline is green. This is the class of incident that takes hours to notice."

4.3 Let it run (about 10 min, talk over it)

Wait for 2 or more anomalous 5-minute buckets. Use the time to walk through the agent's playbook, tools and confirmation rule (section 5).

SELECT bucket_start, n, flag_rate, baseline_rate, z_score, is_anomaly
FROM FRAUD_AUTOML_DEMO.MONITORING.V_FRAUD_RATE_ANOMALY ORDER BY bucket_start DESC LIMIT 6;

4.4 The agent investigates (3-5 min)

cortex automation execute FRAUD_WATCH --wait --timeout 900

In production this runs on its schedule. While it runs, the email and PR arrive. Walk through the email:

  1. Summary and impact (excess declines, cards affected)
  2. Timeline: deploy, then spike, then detected
  3. Evidence chain: spike concentrated in card_cohort = ISSUED_SINCE_NOV; cust_avg_amt_30d null % went from 0 to about 10%; the lineage path leads to CUSTOMER_PROFILE_V2; the deploy touched it
  4. Verification table: pipeline_version V1 brings the rate back to baseline and explains more than 80% of the excess, so CONFIRMED; model V0 and input_asof are ruled out
  5. Revert PR link plus the proposed forward fix
"The agent didn't guess. It re-ran the last 20 minutes of transactions through the previous pipeline version, with the same data and the same model, and the problem disappeared. That's a controlled experiment, not a correlation."

4.5 Human approves (1 min)

# review and merge the agent's PR in GitHub, then CI redeploys main:
uv run python scripts/scenario.py deploy-main

Within 5-10 minutes the anomaly view returns to baseline.

CI note: in this demo, "CI" is the deploy-main command. In production, a GitHub Action (or a Snowflake Git repository plus task) runs the same deploy on merge to main.

4.6 Optional: "it doesn't blame the pipeline for everything" (5 min)

uv run python scripts/scenario.py burst-on     # genuine gift-card fraud attack, no code change
# wait about 10 min, then:
cortex automation execute FRAUD_WATCH --wait --timeout 900
uv run python scripts/scenario.py burst-off

Expected: an UNCONFIRMED verdict. Every revert still shows a high rate, the features are healthy, and the spike is concentrated in merchant_category = GIFT_CARDS. It's labelled a "possible genuine fraud event" and no PR is opened.

6. How this works in production (not a staged incident)

The demo plants one cause, but nothing in the agent is specific to it. The tools are generic, and the agent has to find the cause the same way it would in real life.

Prerequisites (platform hygiene, more important than the agent)

  • Version everything: pipeline code in Git and deployed by CI, with every deploy logged with its SQL and commit; models in the Model Registry; every prediction stamped with model and pipeline version.
  • Replayable features: feature logic is a deterministic function of an as-of window. No CURRENT_TIMESTAMP(), sampling or external calls in the feature path.
  • Point-in-time inputs: Time Travel retention that covers the investigation window (7 days here; up to 90 on Enterprise), or scheduled snapshots for longer windows.
  • Feature log: persist exactly what the model saw, and attach DMFs to it.
  • Lineage: a mapping from each model input to its source columns and owners (Feature Store / Horizon lineage, or a curated catalog).

Detection versus investigation

Detection stays deterministic and cheap: anomaly views, DMF expectations, model monitors and alerts. The LLM agent only starts reasoning when a signal fires. That keeps cost predictable and makes detection auditable.

Most real incidents have no deploy

Upstream systems start sending NULLs, a partner feed is late, a new MCC code appears, or customer behaviour shifts. The same loop covers these: input_asof tests "was it the data?", and the "all reverts fail and the features are healthy" branch catches genuine shifts rather than blaming code.

Honest limits

  • Labels are late: for fraud, the early signal is prediction shape, not accuracy. The agent can prove a change caused the shift before anyone knows whether the predictions were wrong.
  • Concurrent changes: two changes in the window need combination tests, or the agent reports the result as ambiguous.
  • Retention and determinism: if inputs can't be reconstructed, the counterfactual can't run, and the agent must say so.
  • Autonomy boundary: the agent is read-only in Snowflake; remediation is a PR that a human merges. That boundary is what makes it acceptable in a regulated bank.
